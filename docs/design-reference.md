# Us · 我们的小世界

产品需求文档 PRD · 技术架构设计 · 页面原型 · 开发实施规范

(产品方案 V1.0) (微信小程序) (端到端加密)

这次我们不再停留在功能构思阶段，而是把它作为一个正式的软件项目来设计。目标是：**开发人员拿到这份文档，就能开始创建项目、设计数据库、编写接口和实现页面。**

我会把它设计成一个具有完整产品逻辑的双人私密应用，而不是简单地把几个功能堆在一起。

首先确定一个非常重要的架构原则：

**端到端加密与 AI 功能必须进行特殊设计。**

如果日记、照片、信件在上传前已经加密，服务器就不能直接读取它们。因此：

- 普通记录和回忆采用端到端加密。
- AI 整理回忆时，由用户主动选择内容，并明确授权将解密后的内容发送给 AI。
- 未经授权的私人内容绝不进入 AI。
- 不把用户的明文日记保存在服务器上。

这样才能同时保证私密性和 AI 功能的实用性。

另一个原则是：地图只记录用户主动添加的地点，不设计后台持续定位和位置监控。

| 成员 B | 创建、编辑、查看授权范围内的数据 |

两个人拥有平等的空间管理权。

**用户 A 微信登录**

**创建专属空间**

生成一次性邀请二维码 / 邀请码

**用户 B 微信登录并加入**

**建立双人加密空间**

完成密钥协商、设备注册和空间初始化

**进入 Us 首页**

开始记录生活、互动和保存回忆

其中 P0 是上线之前必须完成的功能，P1 是首个完整版本的核心体验，P2 是增强功能。

下面的设计采用一个明确的技术路线：

- 前端：微信原生小程序 + TypeScript。
- 后端：微信云开发 CloudBase。
- 加密：客户端加密、服务端只保存密文。
- 数据同步：云端同步密文，客户端解密。
- AI：用户授权后，单次提交指定内容。
- 地图：主动添加地点，不进行后台定位。
- 设计：自定义温柔手账 UI，不依赖过重的通用组件库。

# 1. 产品设计原则

## 1.1 核心原则

1. 双人专属：每个空间最多两名成员。
2. 数据私密：共同记录与个人记录分别加密。
3. 双向平等：双方拥有相同的基本操作权限。
4. 自愿互动：所有互动功能不设置强制打卡。
5. 长期保存：回忆可以持续积累、查询和导出。
6. 低压力：不通过断签、扣分、惩罚等机制制造负担。
7. 隐私优先：服务器不持有用户的内容解密密钥。

## 1.2 产品范围

V1.0 包含：

- 微信登录及双人绑定。
- 首页与恋爱天数。
- 日记与照片记录。
- 共同时间轴。
- 双人虚拟宠物。
- 时光胶囊。
- 双人足迹地图。
- 月度及年度报告。
- AI 回忆整理。
- 情侣小游戏。
- 纪念日及愿望清单。
- 私人空间和安全设置。

## 1.3 非目标

第一版不开发：

- 社交广场。
- 陌生人匹配。
- 多人群聊。
- 实时位置监控。
- 强制每日签到。
- 情侣关系评分。
- 公开内容推荐。
- 服务器端明文全文搜索。

# 4. 核心特色功能详细需求

## 4.1 双人虚拟宠物 Pet

### 4.1.1 功能目标

创建一只由双方共同照顾的虚拟宠物，让它成为两个人的小伙伴。

### 4.1.2 宠物系统

宠物属性：

| 属性   | 说明               |
| ------ | ------------------ |
| 等级   | 随共同互动逐渐提升 |
| 经验   | 完成互动获得       |
| 饱食度 | 喂食后恢复         |
| 心情   | 互动后改善         |
| 精力   | 休息后恢复         |
| 亲密度 | 双方共同活动积累   |

### 4.1.3 核心操作

- 喂食。
- 抚摸。
- 玩耍。
- 睡觉。
- 更换装饰。
- 查看成长记录。
- 给宠物命名。
- 解锁宠物动作。

### 4.1.4 成长阶段

```text
初始蛋
  ↓
幼年期
  ↓
成长期
  ↓
成年期
  ↓
特殊装扮与纪念形态
```

成长阶段只与累计互动有关，不与连续签到挂钩。

### 4.1.5 宠物小屋

小屋包含：

- 地板。
- 墙纸。
- 床。
- 桌子。
- 玩具。
- 植物。
- 窗户。
- 装饰品。

双方可以共同布置。

### 4.1.6 交互规则

1. 每个用户每天有一定的基础互动次数。
2. 双方操作均可产生经验。
3. 重复操作设置合理上限。
4. 不设置宠物死亡机制。
5. 长期不登录不会造成宠物惩罚。
6. 双方操作冲突时使用版本号和乐观锁解决。
7. 宠物状态密文同步，服务端不读取具体属性。

### 4.1.7 数据模型

```typescript
interface PetState {
  name: string;
  species: string;
  level: number;
  exp: number;
  hunger: number;
  mood: number;
  energy: number;
  intimacy: number;
  decorations: string[];
  lastInteractionAt: number;
  revision: number;
}
```

该对象整体加密后存储。

     ↓

### 4.3.1 功能目标

# 6. 端到端加密架构

这是本项目最重要的技术部分。

## 6.1 加密目标

服务器只能保存：

- 加密后的日记。
- 加密后的照片。
- 加密后的信件。
- 加密后的宠物状态。
- 加密后的地图数据。
- 加密后的报告内容。

服务器不能直接读取这些内容。

## 6.2 加密技术方案

推荐使用经过维护和安全审查的密码学库，不允许自行实现加密算法。

算法设计：

| 用途       | 推荐算法                          |
| ---------- | --------------------------------- |
| 内容加密   | XChaCha20-Poly1305                |
| 密钥交换   | X25519                            |
| 密钥派生   | HKDF-SHA256                       |
| 数字签名   | Ed25519                           |
| 安全随机数 | wx.getRandomValues                |
| 密码派生   | Argon2id 或经过性能测试的安全 KDF |

具体算法库需要在微信开发者工具及真实 iOS、Android 设备中进行兼容性测试。

## 6.3 密钥层级

```text
用户设备
   │
   ├── 用户身份密钥
   │
   ├── 设备密钥
   │
   └── 本地加密存储密钥
          │
          ▼
      双人空间密钥
          │
     ┌────┴────┐
     │         │
  成员 A     成员 B
     │         │
     └────┬────┘
          │
       内容密钥
          │
   ┌──────┼──────┐
   │      │      │
  日记   图片   胶囊
```

个人日记使用个人密钥，不使用共享空间密钥。

共同日记使用共享空间密钥。

## 6.4 密钥初始化

创建空间时：

1. 客户端生成随机空间密钥。
2. 客户端生成身份密钥对。
3. 公开密钥上传服务器。
4. 私有密钥保存在本地受保护的加密存储中。
5. 生成空间恢复密钥。
6. 将空间密钥包装为可恢复的密文备份。
7. 邀请另一位成员。
8. 使用对方已验证的公钥安全传递空间密钥。
9. 双方核对安全码。
10. 加入完成。

服务器不能持有明文空间密钥。

## 6.5 内容加密流程

```text
用户输入内容
      ↓
客户端构造数据对象
      ↓
生成记录唯一 ID
      ↓
根据空间密钥派生记录密钥
      ↓
生成随机 nonce
      ↓
AEAD 加密
      ↓
上传密文
      ↓
服务器存储密文
```

读取时反向执行。

## 6.6 加密数据格式

```typescript
interface EncryptedEnvelope {
  version: 1;
  algorithm: "XCHACHA20-POLY1305";
  keyVersion: number;
  nonce: string;
  ciphertext: string;
}
```

建议额外使用认证附加数据（AAD）绑定：

- spaceId。
- recordId。
- recordType。
- schemaVersion。
- keyVersion。

这样可以防止密文被错误地放到其他记录位置。

## 6.7 文件加密

图片不能明文上传后再在服务器端加密。

正确流程：

```text
选择照片
   ↓
读取本地文件
   ↓
生成文件密钥
   ↓
客户端加密
   ↓
生成加密缩略图
   ↓
上传加密文件
   ↓
云端保存密文
```

大文件建议使用分块加密，每块拥有独立 nonce 和完整性校验。

第一版建议限制图片大小和视频大小，先保证稳定性。

## 6.8 密钥恢复

恢复方式：

- 用户输入恢复密钥。
- 客户端恢复空间密钥。
- 重新注册设备公钥。
- 重新生成设备密钥包装。
- 完成后恢复数据访问。

如果双方丢失所有设备密钥和恢复密钥，数据将无法恢复。

这属于真正端到端加密必须接受的风险。

## 6.9 设备管理

支持：

- 查看已授权设备。
- 添加新设备。
- 移除设备。
- 密钥重新包装。
- 密钥轮换。
- 异常设备提醒。

移除设备不能保证撤回该设备此前已经解密、复制或截图的数据。密钥轮换只能保护未来使用新密钥加密的内容。

## 6.10 元数据保护

以下信息尽量也加密：

- 标题。
- 日记正文。
- 图片名称。
- 地点名称。
- 经纬度。
- 标签。
- 心情。
- 个人备注。

服务器仍可能看到空间成员关系、数据大小、访问时间和请求频率等必要元数据。
